# Internationalisation (EN / FR)

The institution is bilingual. English and French are **equal citizens** — French
is not an afterthought bolted on later.

Library: [next-intl](https://next-intl.dev) v4.

---

## 1. Two separate mechanisms

Don't confuse them:

| What                                     | Mechanism                          | Lives in            |
| ---------------------------------------- | ---------------------------------- | ------------------- |
| UI strings ("Apply now", "Loading…")     | next-intl message catalogues       | `src/messages/*.json` |
| API content (program names, articles)    | Bilingual column pairs from the DB | `name_en` / `name_fr` |

### UI strings

```tsx
// Server Component
const t = await getTranslations("home");
<h1>{t("hero.title")}</h1>

// Client Component
const t = useTranslations("nav");
<span>{t("programs")}</span>
```

### API content

The backend returns **both** columns and lets the client pick:

```tsx
import { localizedField } from "@/lib/i18n-field";

localizedField(program, "name", locale);  // name_fr ?? name_en
```

English is `NOT NULL` in the database; French is nullable. `localizedField`
falls back to English (and treats a blank string as missing).

## 2. Setup

| File                   | Role                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `src/i18n/routing.ts`  | **Single source of truth**: locales, default, prefix strategy |
| `src/i18n/navigation.ts` | Locale-aware `Link`, `useRouter`, `usePathname`, `redirect` |
| `src/i18n/request.ts`  | Per-request config: loads + merges messages, sets time zone  |
| `src/i18n/deep-merge.ts` | Recursive EN-fallback overlay                             |
| `src/proxy.ts`         | Locale negotiation & redirect                                |
| `next.config.ts`       | `createNextIntlPlugin("./src/i18n/request.ts")`               |

Config: locales `["en", "fr"]`, default `en`, `localePrefix: "always"`,
time zone `Africa/Douala` (WAT/UTC+1).

`localePrefix: "always"` means `/en/programs` and `/fr/programs` — never a
bare `/programs`. Every page has one canonical, indexable URL per language.

---

## 3. English fallback

**A missing French string must render English, never a raw key.**

next-intl does *not* fall back across locales on its own, so `request.ts`
deep-merges `fr.json` over `en.json`:

```ts
messages = deepMerge(englishMessages, frenchMessages)
```

The merge is **recursive** on purpose. A shallow spread would let `fr.common`
replace `en.common` wholesale — so any key missing inside that group would vanish
rather than fall back. `deepMerge` also ignores blank strings (`""`), treating
them as "not translated yet".

This is a safety net, not a licence: **ship both languages with the feature.**

---

## 4. Adding strings

1. Add the key to **`en.json` and `fr.json` together**, in the same nested spot.
2. Namespace by feature (`home`, `programs`, `contact.form`) — not by component.
3. Use ICU for plurals and interpolation, not string concatenation:

```json
{
  "duration": "{years, plural, one {# year} other {# years}}",
  "rights": "© {year} Trustech University Institute of Business Management and Biomedical Sciences. All rights reserved."
}
```

```tsx
t("duration", { years: program.duration_years });
```

Concatenating fragments ("`{n}` + ' years'") breaks in French, where agreement
and word order differ. Let ICU handle it.

## 5. Language switcher

`components/layout/language-switcher.tsx` swaps the locale segment while keeping
the current path, so the user stays on the page they were reading.

It reads `usePathname()` from `@/i18n/navigation` (locale-stripped but otherwise
concrete) and calls `router.replace(pathname, { locale })`.

---

## 6. Design constraints

- **EN/FR parity (DP-04)**: every component must render both without truncation
  or overlap. French runs ~15–20% longer than English — never size a button to
  fit the English label exactly.
- Dates, numbers and currency go through `Intl` (`formatDate`, `formatCurrency`
  in `lib/utils.ts`), never manual formatting. `fr-CM` and `en-CM` differ in
  separators and ordering.
- `<html lang>` is set from the locale by the layout — screen readers switch
  pronunciation on it.
- API errors already carry `message_en` + `message_fr`; surface via
  `error.localizedMessage(locale)`.

---

## 7. Translated pathnames (not enabled yet)

Currently both locales share pathnames (`/fr/programs`, not `/fr/programmes`).
The spec eventually wants localized slugs.

Because **all** navigation goes through `@/i18n/navigation`, enabling them is
local: add a `pathnames` map to `defineRouting` in `routing.ts`:

```ts
export const routing = defineRouting({
  locales: ["en", "fr"],
  defaultLocale: "en",
  localePrefix: "always",
  pathnames: {
    "/": "/",
    "/programs": { en: "/programs", fr: "/programmes" },
    "/programs/[slug]": { en: "/programs/[slug]", fr: "/programmes/[slug]" },
    "/about": { en: "/about", fr: "/a-propos" },
  },
});
```

Two things must change with it:

1. `Link` hrefs become the **canonical** (English) pathname; next-intl rewrites
   the display URL. Dynamic routes take the object form:
   `<Link href={{ pathname: "/programs/[slug]", params: { slug } }}>`.
2. The language switcher must pass `{ pathname, params }` (from `useParams()`)
   to `router.replace`, or dynamic segments are lost on switch. There's a comment
   marking the spot.

---

## 8. Adding a locale

1. Add the code to `routing.locales`.
2. Create `src/messages/<code>.json` (copy `en.json`; untranslated keys fall back).
3. Add it to the `languages` alternates in each `generateMetadata` and to
   `sitemap.ts` (it iterates `routing.locales`, so it follows automatically).
4. Add it to the switcher's rendering — it maps `routing.locales`, so it too
   follows automatically.
5. Check layouts at 320px: a longer language may break tight components.
